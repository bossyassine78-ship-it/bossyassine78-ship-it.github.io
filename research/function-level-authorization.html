The endpoint the UI never showed you

A disclosed admin-creation bug highlights why UI visibility and valid login sessions do not establish permission to perform an action.

By Shemkar · Independent analysisPublic source: Dec 20246-minute read
Attribution and scope. Analysis of HackerOne's December 2024 article about a Shopify Stocky privilege-escalation report originally submitted by @stapia. Original finding and evidence are credited to them. This page is my own commentary and testing framework based on public information, not a claim that I discovered or reproduced the original vulnerability. All hypothetical tests refer to systems where testing is authorized.

What the public write-up describes

A standard user account could send a request to an admin-creation function in Shopify's Stocky application. The endpoint accepted an ordinary authenticated session and request token, then performed an action that should have required elevated privileges.

This is a broken function-level authorization issue. It is not necessarily mass assignment: the vulnerable action was protected incorrectly even without adding an unexpected role parameter.

My analysis: authentication versus authority

has_valid_session(user) = true
can_create_admin(user) = false

POST /admin/create
expected: DENY
actual in reported case: ALLOW

Being logged in proves a principal is known; it does not prove that principal may create administrators. An anti-CSRF token provides no substitute for server-side role verification.

The regression matrix I would build

For each sensitive operation, test the action with multiple principals and assert the authorization decision server-side. Cover anonymous, standard user, workspace manager, and administrator roles only if the target's rules define those roles.

  • Can a normal user invoke a privileged function by replaying its request directly?
  • Can a role be changed through a nested object or an extra property, indicating a separate mass-assignment risk?
  • Do alternative HTTP methods, old paths, or GraphQL mutations reach the same operation without the intended check?
  • Is every denied request also checked for a state-changing side effect?

Engineering takeaway

Implement authorization where the state change occurs, not just in navigation or route rendering. Build an explicit principal × action matrix, and require the test suite to fail whenever low-privilege roles can trigger high-privilege effects.
